Reflection (reflect)
reflect.Type, reflect.Value, CanSet, VisibleFields và khi nào reflection thực sự đáng dùng
▼
reflectCanSetVisibleFieldsnâng cao
import (
    "fmt"
    "reflect"
)

type User struct {
    ID   int    `json:"id"`
    Name string `json:"name"`
}

func inspect(v any) {
    rv := reflect.ValueOf(v)
    rt := reflect.TypeOf(v)
    if rt.Kind() == reflect.Pointer {
        rt = rt.Elem()
        rv = rv.Elem()
    }

    fmt.Println(rt.Name(), rt.Kind())

    for _, f := range reflect.VisibleFields(rt) {
        if f.IsExported() {
            value := rv.FieldByIndex(f.Index)
            fmt.Printf("%s tag=%q value=%v\n",
                f.Name, f.Tag.Get("json"), value.Interface())
        }
    }
}

func setName(ptr any, name string) error {
    rv := reflect.ValueOf(ptr)
    if rv.Kind() != reflect.Pointer || rv.Elem().Kind() != reflect.Struct {
        return fmt.Errorf("need pointer to struct")
    }

    field := rv.Elem().FieldByName("Name")
    if !field.IsValid() || !field.CanSet() || field.Kind() != reflect.String {
        return fmt.Errorf("Name is not settable")
    }
    field.SetString(name)
    return nil
}
Ý chính: Reflection cho phép code đọc hoặc thao tác với type và value ở runtime. Nó rất mạnh cho framework, serializer, validator, ORM, DI container, hoặc tooling, nhưng đổi lại là code khó đọc hơn và dễ panic hơn generics hay interface tường minh.
Quy tắc cần nhớ: Muốn sửa field qua reflection, value phải addressable và CanSet() phải trả về true. Field không export hoặc value không phải pointer đúng kiểu thường sẽ không set được. VisibleFields hữu ích khi làm việc với embedding và promoted fields.
Lỗi hay gặp: Gọi Elem() sai ngữ cảnh, FieldByName trên field không tồn tại, hoặc Set trên field không settable đều dễ panic. Một lỗi kiến trúc phổ biến hơn là dùng reflection cho bài toán mà interface, generics, hay code generation giải quyết gọn hơn.
Khi nào dùng: Dùng khi bạn thực sự cần meta-programming ở runtime. Nếu chỉ cần tái sử dụng thuật toán giữa nhiều type, hãy ưu tiên generics trước.

unsafe.Pointer, StringData, Offsetof và các quy tắc không được vi phạm
▼

import (
    "fmt"
    "unsafe"
)

func ReadOnlyBytes(s string) []byte {
    return unsafe.Slice(unsafe.StringData(s), len(s))
}

type Header struct {
    Kind byte
    Len  uint32
    Flag bool
}

var h Header
fmt.Println("sizeof:", unsafe.Sizeof(h))
fmt.Println("align Len:", unsafe.Alignof(h.Len))
fmt.Println("offset Len:", unsafe.Offsetof(h.Len))

// uintptr chỉ là integer, không phải GC root
// Không giữ uintptr từ pointer qua nhiều bước rồi mong runtime "nhớ" object
Ý chính: Package unsafe cho phép đi vòng qua type system để làm những việc rất low-level như kiểm tra layout, zero-copy conversion, hoặc tương tác với ABI/FFI. Đây là vùng tối ưu hóa cực mạnh nhưng cũng là vùng dễ tự bắn vào chân nhất.
Quy tắc cần nhớ: Dữ liệu lấy từ unsafe.StringData không được sửa vì string trong Go là immutable. uintptr không giữ object sống cho GC; nó chỉ là số nguyên. Các phép biến đổi qua unsafe.Pointer phải theo đúng pattern được tài liệu Go cho phép.
Lỗi hay gặp: Người mới hay nhầm “chạy được” với “an toàn”. Nhiều đoạn unsafe có thể chạy ổn hôm nay rồi vỡ ở kiến trúc khác, phiên bản khác, hoặc dưới tải thật. Một lỗi cực nguy hiểm là biến string thành []byte rồi sửa nội dung như thể đó là bộ nhớ mutable hợp lệ.
Đọc sau: Chỉ dùng unsafe khi bạn đã profile xong, hiểu memory model, và thật sự không có lựa chọn thuần Go an toàn hơn.

Khi nào dùng: Dùng khi bạn cần tối ưu theo kiến trúc, hỗ trợ cgo/pure Go song song, hoặc cô lập code chỉ chạy trong test, benchmark, hoặc integration environment.
Testing, benchmarks, fuzzing & synctest
table driven tests, b Loop, fuzzing và testing synctest cho code concurrent trong Go 1.26.4
▼
testingfuzzsynctesttrung cấp
import (
    "context"
    "slices"
    "testing"
    "testing/synctest"
    "time"
)

func TestSplit(t *testing.T) {
    cases := []struct {
        name string
        in   string
        sep  string
        want []string
    }{
        {"comma", "a,b,c", ",", []string{"a", "b", "c"}},
        {"single", "go", ",", []string{"go"}},
    }

    for _, tc := range cases {
        tc := tc
        t.Run(tc.name, func(t *testing.T) {
            got := Split(tc.in, tc.sep)
            if !slices.Equal(got, tc.want) {
                t.Fatalf("Split(%q,%q) = %v, want %v",
                    tc.in, tc.sep, got, tc.want)
            }
        })
    }
}

func BenchmarkSplit(b *testing.B) {
    b.ReportAllocs()
    for b.Loop() {
        Split("a,b,c,d,e", ",")
    }
}

func FuzzParseUser(f *testing.F) {
    f.Add("alice,42")
    f.Fuzz(func(t *testing.T, input string) {
        _, _ = ParseUser(input) // không được panic
    })
}

func TestTimeout(t *testing.T) {
    synctest.Test(t, func(t *testing.T) {
        ctx, cancel := context.WithTimeout(t.Context(), 5*time.Second)
        defer cancel()

        time.Sleep(5 * time.Second)
        synctest.Wait()

        if ctx.Err() != context.DeadlineExceeded {
            t.Fatalf("expected deadline exceeded")
        }
    })
}

// go test -run Split -shuffle=on ./...
// go test -bench=. -benchmem ./...
// go test -fuzz=FuzzParseUser ./...
Ý chính: Testing nâng cao trong Go không chỉ là assert kết quả đúng sai, mà còn gồm benchmark, fuzzing, và kiểm soát hành vi concurrency. Đặc biệt ở Go 1.26.4, testing/synctest là công cụ rất đáng giá để test code concurrent theo thời gian giả lập và bubble cô lập.
Quy tắc cần nhớ: Table-driven tests vẫn là xương sống. Với benchmark mới, b.Loop() giúp quản lý timer tự nhiên hơn. Fuzz target phải “không panic” và giữ invariant của parser/decoder. synctest hợp khi bạn cần kiểm tra timeout, cancellation, hoặc scheduling mà không muốn chờ thời gian thật.
Lỗi hay gặp: Benchmark đo cả setup/cleanup, fuzz test có side effects lên filesystem không kiểm soát, hoặc test concurrency dựa vào time.Sleep ngẫu hứng nên flaky. Ngoài ra, nhiều người quên dùng -shuffle và -benchmem để bắt coupling ẩn và allocation regressions.
Khi nào dùng: Dùng benchmark cho hot path, fuzz cho parser/input boundary, và synctest cho logic concurrent khó tái hiện ổn định bằng clock thật.
log/slog & structured logging
logger theo key value, JSON handlers, WithGroup và logging có cấu trúc trong stdlib
▼
slogJSONHandlerWithGrouptrung cấp
import (
    "context"
    "log/slog"
    "os"
)

logger := slog.New(slog.NewJSONHandler(os.Stdout, &slog.HandlerOptions{
    Level: slog.LevelInfo,
}))

slog.SetDefault(logger)

ctx := context.Background()
reqLog := logger.With("service", "payments").WithGroup("http")

reqLog.InfoContext(ctx, "request finished",
    "method", "POST",
    "path", "/charges",
    "status", 201,
    "duration_ms", 42,
)

slog.Error("db error",
    "err", err,
    "retryable", true,
)
Ý chính: log/slog đưa structured logging vào stdlib, giúp log dễ parse, filter, và đưa vào hệ thống observability hơn kiểu ghép chuỗi bằng fmt.Printf. Đây là hướng mặc định rất ổn cho ứng dụng Go hiện đại.
Quy tắc cần nhớ: Hãy dùng key ổn định, machine-friendly như user_id, request_id, duration_ms. With phù hợp cho context lặp lại, còn WithGroup giúp namespace các field liên quan. InfoContext và họ hàng *Context hợp khi logger cần đi cùng request context.
Lỗi hay gặp: Log quá nhiều object lớn, trộn message format style với key-value style, hoặc dùng key không nhất quán giữa các nơi làm log khó search. Một lỗi nhỏ nhưng khó chịu là truyền số lượng args lẻ, dễ sinh output khó đọc.
Khi nào dùng: Dùng mặc định cho service, CLI, job runner, và app cần tích hợp với JSON logs hoặc log aggregation.
HTTP routing with ServeMux
method aware patterns, PathValue, wildcard segments và rule matching của ServeMux mới
▼
ServeMuxPathValueroutingtrung cấp
mux := http.NewServeMux()

// Method + path
mux.HandleFunc("POST /users", createUser)
mux.HandleFunc("GET /users/{id}", getUser)
// Match đúng root "/"
mux.HandleFunc("GET /{$}", home)
// Wildcard phần còn lại
mux.HandleFunc("GET /static/{path...}", serveStatic)

// GET pattern cũng match HEAD
// Pattern có thể bao gồm cả host: "GET example.com/admin/"

func getUser(w http.ResponseWriter, r *http.Request) {
    id := r.PathValue("id")
    fmt.Fprintf(w, "user=%s", id)
}

func serveStatic(w http.ResponseWriter, r *http.Request) {
    path := r.PathValue("path")
    http.ServeFile(w, r, "static/"+path)
}

log.Fatal(http.ListenAndServe(":8080", mux))
Ý chính: ServeMux hiện đại của Go hỗ trợ pattern theo method, host, wildcard path, và path parameters đủ mạnh cho rất nhiều ứng dụng web thường gặp mà không cần router ngoài.
Quy tắc cần nhớ: Request.PathValue lấy giá trị wildcard đã match. Pattern GET /foo cũng match cả HEAD. /{$} chỉ match đúng root, còn trailing slash hoặc {name...} đại diện subtree. Nếu hai pattern xung đột, việc đăng ký handler có thể panic.
Lỗi hay gặp: Nhầm giữa / và /{$}, hoặc đăng ký pattern chồng chéo rồi ngạc nhiên khi thứ tự đăng ký không “cứu” được xung đột. Ngoài ra, hành vi ServeMux thay đổi đáng kể từ Go 1.22, nên khi đọc code cũ bạn cần nhớ bối cảnh version.
Khi nào dùng: Dùng khi ứng dụng HTTP của bạn không cần middleware/routing quá đặc thù. Đây là lựa chọn ngày càng hợp lý để giảm dependency bề mặt.

Ý chính: Go có thể build sang WebAssembly cho browser hoặc WASI-style hosts. Đây là cách tái sử dụng code Go ở môi trường ngoài tiến trình native, đặc biệt cho sandboxed execution, edge runtimes, hoặc logic chia sẻ giữa backend và host khác.
Quy tắc cần nhớ: GOOS=js GOARCH=wasm nhắm browser/JS host, còn GOOS=wasip1 GOARCH=wasm phù hợp hơn cho WASI. Với build mode dùng //go:wasmexport, bạn cần đúng một main package và host phải thực hiện khởi tạo đúng cách.
Lỗi hay gặp: Nhiều người tưởng mọi package native đều chạy y hệt trong wasm, nhưng host environment và syscall surface rất khác. Một lỗi khác là build được rồi nhưng quên phần bootstrap của host, đặc biệt với WASI reactor cần gọi _initialize.
Đọc sau: WASM với Go vẫn là vùng nên đo và thử tích hợp sớm, vì giới hạn runtime và host API thường quyết định kiến trúc nhiều hơn bản thân cú pháp Go.
CGo & FFI
call C from Go, cgo directives, ownership bộ nhớ và các pointer rules rất dễ sai
▼
cgoCffinâng cao
//go:build cgo

/*
#cgo pkg-config: libpng
#include <stdio.h>
#include <stdlib.h>

void sayHello(const char* name) {
    printf("Hello, %s!\n", name);
}
*/
import "C"
import "unsafe"

func greet(name string) {
    cName := C.CString(name)
    defer C.free(unsafe.Pointer(cName))
    C.sayHello(cName)
}

// Quy tắc quan trọng:
// - Bộ nhớ do C.CString cấp phát phải được C.free
// - Không được đưa Go pointer cho C giữ lại tùy tiện
Ý chính: CGo là cầu nối giữa Go và C khi bạn cần dùng thư viện native, syscall wrapper đặc thù, hoặc ABI bên ngoài. Đây là lựa chọn thực dụng trong nhiều hệ thống, nhưng nó làm build, deploy, debug, và portability phức tạp hơn hẳn pure Go.
Quy tắc cần nhớ: Ownership bộ nhớ phải rất rõ: cái gì do C cấp phát thì phải được C giải phóng đúng chỗ. Truyền con trỏ giữa Go và C phải tuân thủ pointer rules của cgo; đừng giả định rằng “truyền được là an toàn”. CGo thường nên cô lập vào package biên mỏng, không để rò lan khắp codebase.
Lỗi hay gặp: Quên C.free, để C giữ reference tới Go memory quá lâu, hoặc trộn build environments khiến máy CI/CD thiếu compiler/linker phù hợp. CGo cũng hay phá trải nghiệm cross-compile đơn giản vốn là thế mạnh của Go.
Khi nào dùng: Dùng khi pure Go chưa có lựa chọn chấp nhận được hoặc khi bạn bắt buộc tích hợp thư viện native sẵn có. Nếu không bị ép, pure Go gần như luôn là đường nhẹ đầu hơn.
Profile guided optimization
PGO từ workload thật, default pgo auto mode và cách đưa profiling vào vòng tối ưu hiệu năng
▼
pgooptimizationprofilenâng cao
// Thu thập CPU profile từ workload thật hoặc benchmark đại diện
// go test -run=^$ -bench=. -cpuprofile=cpu.prof ./...

// Build với profile cụ thể
// go build -pgo=cpu.prof ./cmd/api

// Hoặc dùng cơ chế mặc định của go build
// mv cpu.prof ./cmd/api/default.pgo
// go build ./cmd/api   // mặc định là -pgo=auto

// Tắt PGO nếu cần so sánh
// go build -pgo=off ./cmd/api
Ý chính: PGO cho compiler thêm dữ liệu thật về đường chạy nóng để cải thiện các quyết định tối ưu như inlining và devirtualization. Đây là kiểu tối ưu có ROI rất tốt vì thường không yêu cầu đổi source code.
Quy tắc cần nhớ: Chất lượng profile quyết định chất lượng tối ưu. Ở Go 1.26.4, go build mặc định dùng -pgo=auto, nghĩa là nếu có file default.pgo cạnh main package thì nó sẽ tự áp dụng. Luôn so sánh trước và sau bằng benchmark hoặc telemetry thật.
Lỗi hay gặp: Dùng profile không đại diện cho production, profile quá cũ, hoặc tưởng PGO sẽ cứu mọi bottleneck. Nếu vấn đề nằm ở I/O, DB, lock contention, hay allocation pattern tệ, PGO không phải thuốc thần.
Khi nào dùng: Dùng khi ứng dụng đã khá ổn về thuật toán và bạn muốn bòn thêm hiệu năng từ hot path bằng dữ liệu thật thay vì micro guessing.

Quy tắc cần nhớ: Dòng go mô tả version ngôn ngữ hoặc tối thiểu của module, còn toolchain gợi ý toolchain nên dùng. go get -tool thêm tool declaration vào go.mod. go work rất tiện cho monorepo hoặc nhiều module local, nhưng không phải lúc nào cũng nên commit vào mọi repo thư viện.
Lỗi hay gặp: Để go.mod bẩn vì quên go mod tidy, cài tool ngoài module rồi hy vọng cả team hoặc CI có cùng phiên bản, hoặc dùng go work local khiến code chạy được trên máy mình nhưng không tái hiện trong CI. Một lỗi khác là lẫn lộn vai trò của module dependency với CLI tool dependency.
Khi nào dùng: Dùng tool cho code generators, linters, và CLI cần pin version; dùng go work khi phát triển nhiều module nội bộ cùng lúc; dùng vendor khi môi trường build yêu cầu source dependencies cục bộ.
