Goroutines, scheduling & WaitGroup
go keyword, lightweight concurrency, sync.WaitGroup và vòng đời của goroutine
▼
goroutineWaitGrouplifecycletrung cấp
var wg sync.WaitGroup

for i := range 3 {
    wg.Go(func() {
        fmt.Println("worker", i)
    })
}
wg.Wait()

func consume(ctx context.Context, jobs <-chan int) {
    go func() {
        for {
            select {
            case job, ok := <-jobs:
                if !ok {
                    return
                }
                fmt.Println("job:", job)
            case <-ctx.Done():
                return
            }
        }
    }()
}
Ý chính: Goroutine là đơn vị concurrency rất nhẹ do runtime Go quản lý. Bạn tạo goroutine bằng từ khóa go, còn WaitGroup giúp chờ một nhóm công việc kết thúc.
Quy tắc cần nhớ: Concurrency không đồng nghĩa với parallelism. WaitGroup chỉ chờ, nó không hủy goroutine và cũng không gom lỗi. Mỗi goroutine nên có đường thoát rõ ràng như close(channel) hoặc ctx.Done().
Lỗi hay gặp: Goroutine rất rẻ nhưng không miễn phí. Nếu goroutine bị kẹt mãi ở send, receive, sleep loop, hay I/O mà không có cơ chế dừng, bạn sẽ tạo goroutine leak.
Khi nào dùng: Dùng goroutine cho các tác vụ độc lập, I/O bound, background work, hoặc chia nhỏ việc cần chạy đồng thời.

// Select với timeout: block cho đến khi có case sẵn sàng
select {
case msg := <-ch1:
    fmt.Println("received:", msg)
case ch2 <- "ping":
    fmt.Println("sent ping")
case <-time.After(500 * time.Millisecond):
    fmt.Println("timeout")
}

// Non-blocking select: dùng default khi muốn kiểm tra nhanh
select {
case msg := <-ch1:
    fmt.Println("received immediately:", msg)
default:
    fmt.Println("no channel ready")
}
Ý chính: Channel là cách Go đồng bộ và truyền dữ liệu giữa goroutines. select cho phép chờ nhiều thao tác channel cùng lúc.
Quy tắc cần nhớ: Thông thường bên gửi là bên đóng channel. Receive từ channel đã đóng sẽ trả về zero value cùng ok = false. Send vào channel đã đóng sẽ panic. Nil channel sẽ block mãi.
Lỗi hay gặp: Nhiều người trộn default với time.After trong cùng một select rồi tưởng rằng đang chờ timeout, nhưng default sẽ làm select trở thành non-blocking. Ngoài ra, đóng channel từ phía receiver thường là dấu hiệu thiết kế chưa ổn.
Khi nào dùng: Dùng channel khi bạn cần giao tiếp hoặc đồng bộ hóa giữa goroutines. Nếu chỉ cần bảo vệ shared state đơn giản, Mutex thường thẳng và dễ hiểu hơn.
Pipelines, fan-out/fan-in & cancellation
pipeline stages, close propagation, early stop và tránh leak bằng context
▼
pipelinefan-outfan-incancellationnâng cao
func gen(ctx context.Context, nums ...int) <-chan int {
    out := make(chan int)
    go func() {
        defer close(out)
        for _, n := range nums {
            select {
            case out <- n:
            case <-ctx.Done():
                return
            }
        }
    }()
    return out
}

func sq(ctx context.Context, in <-chan int) <-chan int {
    out := make(chan int)
    go func() {
        defer close(out)
        for n := range in {
            select {
            case out <- n * n:
            case <-ctx.Done():
                return
            }
        }
    }()
    return out
}
Ý chính: Pipeline chia xử lý thành nhiều stage nối với nhau bằng channel. Fan-out cho nhiều worker cùng xử lý một input stream, còn fan-in gộp nhiều output stream về một nơi.
Quy tắc cần nhớ: Mỗi stage thường đóng channel đầu ra của chính nó, không đóng channel đầu vào của stage khác. Nếu consumer có thể dừng sớm, nên có cơ chế cancellation để upstream không bị kẹt lúc gửi tiếp dữ liệu.
Lỗi hay gặp: Pipeline rất dễ sinh goroutine leak nếu một stage phía sau đọc chưa hết nhưng phía trước vẫn cố gửi tiếp. Đây là lý do context hoặc done channel thường đi kèm pattern này.
Khi nào dùng: Dùng cho các luồng xử lý nhiều bước như parse - transform - validate - save, hoặc khi muốn tách rõ từng stage đồng thời.
Worker pool & bounded concurrency
jobs/results channels, fixed workers, backpressure và giới hạn số tác vụ chạy song song
▼
worker poolboundedbackpressuretrung cấp
type Job struct{ ID int }
type Result struct {
    JobID int
    Value int
}

func worker(jobs <-chan Job, results chan<- Result, wg *sync.WaitGroup) {
    defer wg.Done()
    for job := range jobs {
        results <- Result{JobID: job.ID, Value: job.ID * job.ID}
    }
}

jobs := make(chan Job, 100)
results := make(chan Result, 100)
var wg sync.WaitGroup

for range 3 {
    wg.Add(1)
    go worker(jobs, results, &wg)
}
Ý chính: Worker pool là pattern rất phổ biến để giới hạn số goroutine chạy đồng thời. Thay vì spawn vô hạn goroutine, bạn giữ một số worker cố định và đẩy việc qua channel.
Quy tắc cần nhớ: Worker pool tạo bounded concurrency, giúp tránh quá tải CPU, DB, disk, network, hoặc API ngoài. Buffered channel thường đóng vai trò queue và cũng tạo backpressure khi queue đầy.
Lỗi hay gặp: Quên đóng jobs hoặc quên đóng results sau khi worker xong sẽ làm consumer bị treo. Spawn quá nhiều worker cũng không giúp nhanh hơn nếu bottleneck nằm ở tài nguyên ngoài.
Khi nào dùng: Dùng khi có nhiều job giống nhau cần xử lý song song nhưng bạn muốn khống chế mức độ song song.
Mutex, RWMutex, Once & race detector
shared state, map safety, sync.Once, chọn primitive phù hợp và phát hiện data race
▼
MutexRWMutexsync.Onceracetrung cấp
type SafeCounter struct {
    mu sync.RWMutex
    v  map[string]int
}

func NewSafeCounter() *SafeCounter {
    return &SafeCounter{
        v: make(map[string]int),
    }
}

func (c *SafeCounter) Inc(key string) {
    c.mu.Lock()
    defer c.mu.Unlock()
    c.v[key]++
}

func (c *SafeCounter) Value(key string) int {
    c.mu.RLock()
    defer c.mu.RUnlock()
    return c.v[key]
}

c := NewSafeCounter()
c.Inc("go")
fmt.Println(c.Value("go")) // 1

var once sync.Once

func initDB() {
    fmt.Println("initialize once")
}

func GetDB() {
    once.Do(initDB)
}

// go test -race ./...
Ý chính: Khi nhiều goroutine cùng truy cập shared memory, bạn cần primitive đồng bộ như Mutex hoặc RWMutex. sync.Once giúp một đoạn init chỉ chạy đúng một lần.
Quy tắc cần nhớ: Map thường không thread-safe cho concurrent read/write. RWMutex chỉ hữu ích khi số reader nhiều hơn write đáng kể. Không copy value chứa mutex sau khi nó đã bắt đầu được dùng. Với wrapper như SafeCounter, bạn cũng phải khởi tạo map bên trong trước khi ghi.
Lỗi hay gặp: Nhiều bug concurrency không lộ ngay mà chỉ xuất hiện khi tải cao. Hãy chạy go test -race hoặc go run -race khi nghi có data race. sync.Map không phải thay thế mặc định cho mọi map thường.
Khi nào dùng: Dùng mutex khi nhiều goroutine cần sửa cùng một state trong memory. Đây thường là lựa chọn đơn giản và đúng hơn so với cố “channel hóa” mọi thứ.
Context
cancellation, deadlines, request-scoped values và propagation qua nhiều goroutine
▼
contextcancellationdeadlinetrung cấp
base := context.Background()
ctx, cancel := context.WithTimeout(base, 5*time.Second)
defer cancel()

type ctxKey struct{}
ctx = context.WithValue(ctx, ctxKey{}, "user-123")

func fetchData(ctx context.Context, url string) ([]byte, error) {
    req, _ := http.NewRequestWithContext(ctx, "GET", url, nil)
    resp, err := http.DefaultClient.Do(req)
    if err != nil {
        if errors.Is(err, context.DeadlineExceeded) {
            return nil, fmt.Errorf("timeout: %w", err)
        }
        return nil, err
    }
    defer resp.Body.Close()
    return io.ReadAll(resp.Body)
}
Ý chính: context mang tín hiệu hủy, deadline, và metadata theo request xuyên qua nhiều hàm và goroutine. Đây là primitive rất quan trọng trong code server, CLI, background jobs, và network I/O.
Quy tắc cần nhớ: Context nên là tham số đầu tiên, tên ctx. Không lưu context trong struct. Luôn gọi cancel() nếu API trả về hàm cancel. WithValue chỉ dành cho request-scoped metadata, không phải chỗ nhét tùy tiện mọi tham số.
Lỗi hay gặp: Quên cancel có thể giữ timer và resource lâu hơn cần thiết. Nhiều người cũng lạm dụng WithValue như một global map ẩn, khiến code khó đọc và khó kiểm soát type.
Khi nào dùng: Dùng khi một tác vụ có thể bị hủy, có deadline, hoặc cần truyền metadata đi qua nhiều tầng xử lý.

Ý chính: Atomic operations cho phép đọc/ghi một số trạng thái đơn giản mà không cần lock rõ ràng. Chúng hữu ích cho counters, flags, state transitions, hoặc snapshot config nhỏ.
Quy tắc cần nhớ: Atomic phù hợp với state đơn giản và invariant hẹp. Nếu một thao tác liên quan nhiều field hoặc nhiều bước phải nhất quán cùng nhau, mutex thường đúng và dễ hiểu hơn.
Lỗi hay gặp: Không được trộn access atomic và non-atomic trên cùng một biến. Atomic code “không khóa” nhưng không có nghĩa là dễ đúng; CAS loop và memory ordering dễ làm code khó đọc và khó review.
Đọc sau: Nếu chưa có áp lực hiệu năng rõ ràng, hãy ưu tiên mutex trước. Atomic là công cụ mạnh nhưng nên dùng tiết chế.
errgroup & singleflight
golang.org/x/sync, fail-fast coordination, parallel error handling và request deduplication
▼
errgroupsingleflightx/syncnâng cao
import (
    "golang.org/x/sync/errgroup"
    "golang.org/x/sync/singleflight"
)

eg, ctx := errgroup.WithContext(context.Background())
eg.Go(func() error { return task1(ctx) })
eg.Go(func() error { return task2(ctx) })

if err := eg.Wait(); err != nil {
    return err
}

var sf singleflight.Group

func fetchUser(id string) (*User, error) {
    v, err, shared := sf.Do(id, func() (any, error) {
        return db.GetUser(id)
    })
    _ = shared
    return v.(*User), err
}
Ý chính: errgroup rất hợp khi nhiều goroutine cùng phục vụ một tác vụ lớn và chỉ cần một lỗi là nên fail-fast. singleflight giúp deduplicate nhiều request giống nhau đang diễn ra cùng lúc.
Quy tắc cần nhớ: errgroup thường là lựa chọn tốt hơn WaitGroup khi bạn cần gom lỗi và hủy sibling tasks theo context. singleflight chỉ gộp lời gọi trùng key tại cùng thời điểm, nó không phải cache.
Lỗi hay gặp: Dùng singleflight rồi tưởng rằng dữ liệu đã được lưu lại cho lần gọi sau. Hoặc dùng WaitGroup thủ công trong bài toán fail-fast làm code dài và khó kiểm soát hơn mức cần thiết.
Khi nào dùng: Dùng errgroup cho parallel sub-tasks kiểu fetch nhiều nguồn rồi tổng hợp. Dùng singleflight để tránh cache stampede hoặc duplicate expensive calls.
