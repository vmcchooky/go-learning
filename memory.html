Escape analysis, stack & heap
compiler quyết định object ở stack hay heap, đọc gcflags -m và hiểu escape đúng bản chất
▼
escape analysisstackheaptrung cấp
// Xem compiler giải thích vì sao value escape
// go build -gcflags="-m" ./...

func newFoo() *Foo {
    f := Foo{} // địa chỉ thoát khỏi function, nên thường lên heap
    return &f
}

func PrintAny(v any) {
    fmt.Println(v) // boxing vào interface có thể góp phần làm value escape
}

func makeBuf(n int) []byte {
    return make([]byte, n) // backing array gần như chắc chắn ở heap
}

func sum(nums []int) int {
    total := 0 // thường ở stack nếu không escape
    for _, n := range nums {
        total += n
    }
    return total
}
Ý chính: Trong Go, bạn không “chọn stack hay heap” bằng cú pháp. Compiler tự quyết định dựa trên escape analysis: nếu một value cần sống lâu hơn frame hiện tại hoặc compiler không chứng minh được nó an toàn trên stack, value đó sẽ escape lên heap.
Quy tắc cần nhớ: Trả về pointer, lưu vào interface, tạo closure bắt biến, hoặc cấp phát backing array lớn/dynamic đều có thể khiến value escape. Heap không phải là “sai”; vấn đề chỉ xuất hiện khi allocation và GC pressure thật sự trở thành bottleneck.
Value vs pointer: Đừng mặc định dùng *T chỉ vì sợ copy. Với struct nhỏ hoặc không cần shared mutation, value semantics thường đơn giản hơn, locality tốt hơn, và giảm cơ hội tạo aliasing/escape không cần thiết. Pointer chỉ thực sự đáng khi object lớn, cần mutate state chung, hoặc API tự nhiên đã mang ngữ nghĩa tham chiếu.
Interface boxing: Khi một value được gói vào any hay interface khác, compiler có thể phải “box” nó và điều đó có thể góp phần tạo allocation ẩn. Đây là một lý do các API hiệu năng cao thường ưu tiên typed parameters thay vì nhận mọi thứ qua any.
Lỗi hay gặp: Nhiều người cố viết code kỳ quặc chỉ để ép mọi thứ ở stack. Điều đó thường làm code khó đọc mà lợi ích không đáng kể. Hãy xem output -gcflags=-m như tín hiệu để hiểu compiler, không phải cuộc thi “zero heap allocations” trong mọi nơi.
Khi nào dùng: Dùng escape analysis khi bạn đang điều tra allocation bất ngờ, một benchmark chậm, hoặc nghi ngờ một thay đổi nhỏ làm tăng áp lực GC.
Slices, strings & accidental retention
subslice, substring, backing array retention và cách thả reference đúng lúc
▼
slicestringretentiontrung cấp
blob := make([]byte, 10<<20) // 10 MiB
header := bytes.Clone(blob[:128])
fmt.Println(len(header)) // chỉ giữ lại 128 bytes thực sự cần

bigText := strings.Repeat("x", 1<<20)
title := strings.Clone(bigText[:80])
fmt.Println(len(title))

type Node struct{ ID int }

items := []*Node{{ID: 1}, {ID: 2}, {ID: 3}}
n := len(items) - 1
last := items[n]
items[n] = nil // bỏ reference cũ trước khi reslice
items = items[:n]
_ = last

scratch := make([]*Node, 1000)
clear(scratch) // zero các phần tử, nhưng backing array vẫn còn đó
scratch = nil  // bỏ luôn slice nếu không còn dùng nữa
Ý chính: Slice và string thường chia sẻ backing storage với giá trị gốc. Nếu bạn chỉ giữ một mẩu nhỏ của dữ liệu lớn bằng subslice hoặc substring, toàn bộ vùng nhớ lớn đó có thể vẫn bị giữ lại trong memory.
Quy tắc cần nhớ: Khi thực sự cần giữ lại một phần nhỏ lâu dài, hãy copy ra vùng nhớ mới bằng bytes.Clone hoặc strings.Clone. Khi bỏ phần tử khỏi slice chứa pointer, interface, string, map, hoặc slice khác, nên clear slot cũ nếu backing array còn sống lâu.
Lỗi hay gặp: Nhiều người nghĩ s = s[:0] hoặc clear(s) là “trả memory cho OS”. Không hẳn. Chúng chủ yếu giúp tái sử dụng hoặc thả references; backing array vẫn có thể còn được giữ lại cho đến khi không còn ai trỏ tới nó.
Khi nào dùng: Dùng các kỹ thuật này khi xử lý file lớn, request body lớn, log lines dài, hoặc bất kỳ container nào giữ reference đến object nặng.
Preallocation, growth & buffer reuse
make với len cap, slices.Grow, strings.Builder và pattern giảm allocations lặp lại
▼
preallocationcapacityreusetrung cấp
nums := []int{1, 2, 3, 4}
out := make([]int, 0, len(nums))
for _, n := range nums {
    out = append(out, n*n)
}
fmt.Println(out)

// Khi biết cần append thêm n phần tử, có thể grow trước
out = slices.Grow(out[:0], 16)

var b strings.Builder
b.Grow(64)
for _, part := range []string{"Go", " ", "memory"} {
    b.WriteString(part)
}
fmt.Println(b.String())

buf := make([]byte, 0, 4096)
buf = append(buf, "hello"...)
buf = buf[:0] // reuse scratch buffer nếu vẫn cùng owner
Ý chính: Nhiều bài toán chậm không phải do thuật toán tệ, mà do tạo quá nhiều allocation nhỏ lặp đi lặp lại. Preallocation và reuse đúng chỗ giúp giảm pressure lên allocator và GC rất hiệu quả.
Quy tắc cần nhớ: make([]T, len) tạo ra slice đã có phần tử, còn make([]T, 0, cap) là mẫu chuẩn khi bạn sẽ append. slices.Grow hữu ích khi biết mình sắp append thêm bao nhiêu phần tử. strings.Builder hợp cho ghép string lặp lại.
Unsafe / advanced: Nếu thật sự cần zero-allocation đổi []byte -> string, Go hiện đại có unsafe.String(unsafe.SliceData(b), len(b)). Đây là kỹ thuật rất mạnh nhưng string mới sẽ dùng chung vùng nhớ với slice, nên byte slice đó không được mutate nữa khi string còn sống.
Lỗi hay gặp: Preallocate quá lớn cũng là lãng phí memory. Một lỗi khác là tái sử dụng scratch buffer rồi vô tình trả slice đó ra ngoài, khiến caller giữ luôn backing array nội bộ lâu hơn cần thiết.
Khi nào dùng: Dùng trong hot path như parsing, serialization, xử lý text, xây response, hoặc transform list lớn trong vòng lặp.
GC tuning, GOGC & GOMEMLIMIT
runtime debug knobs, soft memory limit, MemStats và khi nào nên đụng vào tuning
▼

oldGC := debug.SetGCPercent(100) // tương đương GOGC=100
defer debug.SetGCPercent(oldGC)

oldLimit := debug.SetMemoryLimit(512 << 20) // soft limit ~512 MiB
defer debug.SetMemoryLimit(oldLimit)

var m runtime.MemStats
runtime.ReadMemStats(&m)
fmt.Printf("heap=%d MiB, objects=%d, nextGC=%d MiB\n",
    m.HeapAlloc>>20, m.HeapObjects, m.NextGC>>20)

// GOMEMLIMIT cũng có thể cấu hình qua env từ lúc process khởi động
// GOGC điều khiển tần suất GC tương đối theo live heap
Ý chính: Go GC mặc định đã khá tốt. GOGC và GOMEMLIMIT là hai núm chính để điều chỉnh trade-off giữa CPU và memory footprint, nhưng chúng chỉ nên đụng tới khi đã đo đạc và hiểu workload.
Quy tắc cần nhớ: GOGC là target tăng trưởng heap tương đối sau mỗi chu kỳ GC; thấp hơn nghĩa là gom rác thường xuyên hơn. GOMEMLIMIT là soft memory limit, runtime sẽ cố tôn trọng bằng cách tăng cường GC và trả memory về hệ điều hành tích cực hơn.
Lỗi hay gặp: Đặt memory limit quá thấp có thể khiến chương trình gần như chỉ lo chạy GC. Tắt GC hoặc hạ GOGC mù quáng cũng thường phản tác dụng. Đa số vấn đề memory đến từ allocation pattern và object lifetime, không phải do thiếu tuning.
Khi nào dùng: Dùng khi bạn deploy trong container, cần giữ RSS trong ngưỡng nhất định, hoặc đang benchmark để tìm điểm cân bằng CPU và memory.
sync.Pool
object pooling, temporary buffers, GC interaction và những chỗ sync.Pool không phù hợp
▼
sync.Poolpoolingreusenâng cao
const maxPooledBufferCap = 64 << 10 // 64 KiB

var bufPool = sync.Pool{
    New: func() any {
        return &bytes.Buffer{}
    },
}

func encode(data any) ([]byte, error) {
    buf := bufPool.Get().(*bytes.Buffer)
    defer func() {
        // Reset chỉ đưa len về 0; buffer quá lớn nên bỏ cho GC thu gom.
        buf.Reset()
        if buf.Cap() <= maxPooledBufferCap {
            bufPool.Put(buf)
        }
    }()

    if err := json.NewEncoder(buf).Encode(data); err != nil {
        return nil, err
    }

    out := make([]byte, buf.Len())
    copy(out, buf.Bytes()) // copy ra vùng nhớ riêng trước khi Put lại
    return out, nil
}
Ý chính: sync.Pool giúp tái sử dụng object tạm thời giữa nhiều goroutine để giảm allocation pressure. Nó đặc biệt hợp cho bytes.Buffer, encoder/decoder scratch objects, hoặc temporary structs dùng đi dùng lại.
Quy tắc cần nhớ: Item trong pool có thể bị runtime bỏ đi bất cứ lúc nào, nhất là qua các chu kỳ GC. Vì vậy pool không phải cache bền vững. Luôn reset object trước khi Put, không copy sync.Pool sau khi đã bắt đầu dùng, và thường nên đặt ngưỡng để buffer quá lớn không quay lại pool.
Lỗi hay gặp: Một bug phổ biến là trả object về pool rồi vẫn giữ slice/string trỏ vào bộ nhớ bên trong object đó. Ví dụ trên copy dữ liệu ra out trước khi Put lại buffer chính là để tránh lỗi kiểu này. Một bẫy khác là chỉ gọi Reset() rồi trả luôn các buffer "quái vật" về pool, khiến RSS bị phình ra lâu hơn cần thiết.
Khi nào dùng: Dùng khi profiling cho thấy allocation của object tạm thời lặp lại rất nhiều dưới tải thật. Nếu workload hiếm, object lớn bất thường, hoặc lifecycle gắn với một object ngắn hạn riêng lẻ, pool có thể không đáng dùng.
AddCleanup, finalizers & KeepAlive
cleanup APIs hiện đại, safety net cho resource wrappers và vì sao Close vẫn là con đường chính
▼
AddCleanupfinalizerKeepAlivenâng cao
type Resource struct {
    id      int
    cleanup runtime.Cleanup
    closed  bool
}

func release(id int) {
    fmt.Println("release", id)
}

func NewResource(id int) *Resource {
    r := &Resource{id: id}
    r.cleanup = runtime.AddCleanup(r, release, id)
    return r
}

func (r *Resource) Close() {
    if r.closed {
        return
    }
    r.closed = true
    r.cleanup.Stop()
    release(r.id)
}

func useResource(r *Resource) {
    fmt.Println("use", r.id)
    runtime.KeepAlive(r) // giữ r reachable đến hết điểm này nếu cần
}
Ý chính: Trong Go hiện đại, runtime.AddCleanup là API an toàn hơn để gắn cleanup logic vào object wrapper. Tuy nhiên cleanup/finalizer chỉ là safety net cho resource không phải memory; đường chính vẫn luôn là explicit Close.
Quy tắc cần nhớ: Cleanup không được đảm bảo chạy trước khi process kết thúc, cũng không phải cơ chế quản lý vòng đời chính xác. runtime.SetFinalizer vẫn tồn tại nhưng new code thường nên ưu tiên AddCleanup. Nếu bạn thật sự làm việc ở tầng thấp, runtime.KeepAlive giúp tránh cleanup/finalizer chạy quá sớm.
Lỗi hay gặp: Nhiều người dựa vào finalizer để đóng file, flush buffer, hay giải phóng resource quan trọng một cách quyết định. Điều đó rất mong manh. Một bẫy khác là để callback hoặc argument của cleanup giữ ngược lại pointer gốc, khiến object không bao giờ collect được.
Đọc sau: Đây là vùng kiến thức khá low-level. Bạn chỉ thật sự cần nó khi viết resource wrappers, runtime-adjacent code, cgo bindings, hoặc thư viện quản lý handle đặc biệt.
Profiling, pprof & runtime metrics
heap profile, CPU profile, runtime/metrics, MemStats và quy trình đo trước khi tối ưu
▼
pprofmetricsMemStatsnâng cao
import (
    "net/http"
    "os"
    "runtime"
    "runtime/metrics"
    "runtime/pprof"
    _ "net/http/pprof"
)

// Mở HTTP pprof endpoints
go http.ListenAndServe("localhost:6060", nil)
f, _ := os.Create("cpu.prof")
_ = pprof.StartCPUProfile(f)
defer func() {
    pprof.StopCPUProfile()
    f.Close()
}()

samples := []metrics.Sample{
    {Name: "/gc/heap/live:bytes"},
    {Name: "/memory/classes/total:bytes"},
    {Name: "/memory/classes/heap/released:bytes"},
}
metrics.Read(samples)
for _, sample := range samples {
    fmt.Println(sample.Name, sample.Value.Uint64())
}

runtime.GC()
heapFile, _ := os.Create("heap.prof")
defer heapFile.Close()
_ = pprof.WriteHeapProfile(heapFile)

// go tool pprof http://localhost:6060/debug/pprof/heap
// go tool pprof -http=:8080 cpu.prof
Ý chính: Muốn tối ưu memory đúng cách, bạn phải đo. pprof cho biết allocation và retention đang xảy ra ở đâu, còn runtime/metrics và runtime.ReadMemStats hữu ích cho telemetry, dashboards, và quick inspection trong runtime.
Quy tắc cần nhớ: Heap profile là ảnh chụp gắn với chu kỳ GC gần nhất, còn ReadMemStats cập nhật số liệu đến thời điểm gọi. runtime/metrics phù hợp khi bạn cần lấy một vài counters cụ thể với API ổn định hơn cho quan sát lâu dài.
Lỗi hay gặp: Tối ưu trước khi profile thường dẫn tới sửa sai chỗ. Một lỗi khác là chỉ nhìn tổng RSS rồi kết luận có leak, trong khi thực tế có thể là transient spike, idle heap chưa trả hết, hoặc object lifetime dài hơn dự kiến chứ không phải “leak thật”.
Khi nào dùng: Dùng khi chương trình tăng RAM bất thường, GC CPU cao, latency spike dưới tải, hoặc bạn cần chứng minh một tối ưu memory có thật sự hiệu quả không.
